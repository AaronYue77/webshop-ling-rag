# WebShop 输入与回答格式

用户直接用自然语言提问，可以带上用途、预算、颜色、材质、尺寸、设备型号或排除条件，也可以按上一轮展示的序号追问。网页会传入必要的对话上下文。

| 阶段 | 输入 | 输出 |
| --- | --- | --- |
| 规划 | `question` 原问题、`questionId`、`context` 中的前一次搜索、商品序号及当前商品 | `plan` 包含搜索、详情或比较，及任务、预算、材质等必要条件、排除条件和所指商品 |
| 检索 | 模型计划和 WebShop 目录 | 候选编号、商品 ASIN、原始排序、分类、描述、快照价、规格与缺失字段 |
| 核选和回答 | 原问题、`questionId`、`catalog` 目录证据 JSON 字符串，含 `action`、`tasks`、`result_limit`、`products` 及模型规划中的 `required_terms`、`excluded_terms` | `paragraphs` 为自然正文，`selections` 为新搜索中经过核选的商品编号和证据原文。若任务要求推荐，每个入选商品还包含模型生成的 `reason` |
| 页面 | 正文与通过校验的商品 | 可折叠的查找与核对依据 → 正式回答与逐款理由 → 图片 → 商品目录来源 |

## 正文写法

通常写一到三个完整段落。先直接回答核心问题，再把商品特点、推荐理由或比较取舍写在一起。会影响选择的资料缺口集中说明一次。简单问题用一段即可。用户明确要求清单或多个步骤时，相关事实放在同一项里。

用户要求颜色、尺码或历史价格时，模型按任务和目录字段逐项答复。模型给出的逐款推荐理由按商品展示顺序放在正式回答框内。图片卡展示请求的目录选项，使用 `specs` 核对规格时也会展示已记录的颜色和可选尺码。展开回答前的「查找与核对依据」可以查看目录条件、任务和资料缺口。搜索请求要求历史价格时，正式回答框会标明目录缺少历史价格序列，以未标注日期的目录快照呈现已有金额。

新搜索先在 Kaggle 按模型规划中的必要词和排除词校验目录证据，再由 Ling 按原问题逐件核对商品种类、材质、用途及其他硬条件。只产生一件合格候选时，就推荐一件并说明原因。目录证据校验后没有候选时，Kaggle 服务直接说明本次检索没有找到可确认的商品。

详情和比较沿用上一份清单中的商品编号。Kaggle 在比较请求中提供已知的快照价、最低和最高价对应的原序号、差价及缺失的编号。按美分做差，缺少应比较的编号或价格时保留可核实的金额。Ling 为这两种追问直接生成正文，服务将正文包装为 `paragraphs`，并返回空的 `selections`。

当计划同时要求搜索并引用已展示商品时，Kaggle 让模型只复核本轮动作。核对原商品的规格或兼容性进入详情，明确要求找相似款或替代品时进入搜索。

## 推荐示例

> 我想买一双黑色男士皮鞋，请你推荐几双，并告诉我为什么。

下方是期望输出示例。假设检索的第 1 个候选是网面运动鞋，第 2 个是有皮革鞋面目录证据的 ECCO 乐福鞋。每项 `quote` 都必须能在该候选的目录内容里找到。

```json
{
  "paragraphs": [
    "可以先看 ECCO 的黑色平头乐福鞋。目录列有黑色选项。如果你告诉我常穿的尺码和预算，我可以继续帮你筛。"
  ],
  "selections": [
    {"position": 2, "quote": "full-grain ECCO leather", "reason": "皮革鞋面符合你的材质要求，套穿设计适合日常通勤。"}
  ]
}
```

`position` 是本轮原始召回的编号。网页按 `selections` 的顺序重新生成展示序号，所以上例只展示 ECCO，并把它编号为第 1 款。对话导出仍记录原始两件召回商品及排序，引用只记录展示的商品。

| 问法 | 期望输出 |
| --- | --- |
| 推荐几件预算内的商品 | 先说符合条件的选择，再说明每款适合什么需求。预算只按有依据的目录价或规格价核对。 |
| 比较第一款和第三款 | 先回答最关心的差别，再解释差价或用途取舍。两款保留上一轮的编号。 |
| 第三款是什么材质，39 码能买到吗？ | 连贯写出已知材质和尺码记录，区分尺码表、可选规格与实时库存。 |
| 推荐有某个接口的配件，别推荐转接器 | 按原问题核对接口、兼容型号和排除条件，无法从目录确认兼容性时说明。 |

接口会校验输出结构、候选编号和逐款理由。当模型给出的引句可以在所选商品中逐字定位时，接口保留该引句。若引句被改写、遗漏或来自其他商品，接口从同一商品的目录字段提取原文，优先采用已核对的必要条件、兼容线索和目标尺码。商品与问题的语义匹配由 Kaggle 上的模型判断。推理协议为 `4`，需用与网页配套的 [Kaggle 推理 Notebook](../kaggle/webshop-ling-inference.ipynb)。

## 回答失败诊断

Kaggle 的 `/kaggle/working/webshop-inference.jsonl` 按 `question_id` 记录 `answer_retry` 和 `invalid_answer`。`attempt` 从 `1` 开始，`output_shape` 记录 JSON 是否能解析、顶层类型、缺少的必需字段、额外字段数量，以及 `paragraphs` 和 `selections` 的类型和数组长度。解析失败时还会记录行号和列号。仅包含额外字段且其余校验通过的回答仍会正常返回。

需要检查具体输出时，可在自己的推理 Notebook 副本把 `CAPTURE_INVALID_MODEL_OUTPUT` 改为 `True`，重新运行并复现问题。默认日志中的 `answer_debug_enabled` 会给出 Kaggle 临时私有文件的路径。该文件只记录未通过验证的尝试，每次最多保留 4,096 个字符的模型输出，另记录服务补入的 JSON 前缀。模型可能把对话内容复述到输出中，请仅在自己的会话中查看，诊断后将开关改回 `False`。
